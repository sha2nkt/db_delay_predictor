- **Upstream resilience** (2026-07-25, hardened 2026-08-13 and 2026-08-21) — bahn.de session recycling and fingerprint rotation on Akamai 403s, shared-task caches for journeys/locations (journey departures floored to 5-min buckets so "now" searches share keys, TTL 300 s), upstream fan-out capped at 4 concurrent requests, and successful journeys remembered ≤ 1 h — per exact key and per route (from, to, dticket), the route entry serving newer departure buckets of the same travel day, and since 2026-08-13 only within 30 min of the requested departure, so "now" searches survive bucket rollover without a search ever being answered for another time of day — and re-served with a visible age (`staleSeconds`, `Cache-Control: no-store`) when bahn.de refuses; the frontend auto-retries once behind a friendly "DB-Server überlastet" status, and sustained 429 pressure (≥ 8 in 5 min) pushes an ntfy alert (30-min cooldown). Since the 2026-08-13 evening hardening there is **no identity rotation on 429** (the morning's jar swap + profile rotation was removed as rate-limit evasion): a real circuit breaker guards all journey/location calls — 5 failures in a rolling 60 s open it, cooldown 30 s doubling to a 300 s cap with jitter, an upstream `Retry-After` (delta-seconds or HTTP-date) respected up to the cap and opening it immediately, 1 half-open probe closing or reopening it, and a wholesale 403 block force-opening it for 30 s. Failures carry a typed taxonomy (`UpstreamRateLimited/Blocked/Unavailable/ProtocolError`) mapped to honest statuses: upstream throttle/outage with no stale → 503 + `Retry-After`, unusable response → 502, DelayBahn's own per-IP search limit (burst 10/10 s, 40/min via `cf-connecting-ip`) → 429. Coalesced fetches ride `asyncio.shield`, so one waiter's disconnect can't kill the shared task; `/health` exposes circuit state + pipeline counters; all knobs are env vars (`BAHN_*`, `CLIENT_SEARCH_*`) with safe defaults; state is per-process (global on the single-worker deployment). Same-day follow-up after the breaker itself caused an outage (one 429 blacked out every user for the 45 s bahn.de asked for, while the browser's fixed 4.5 s retry landed inside that window and failed for certain): a named `Retry-After` is now used verbatim rather than max'd against the escalation ladder, the frontend waits the advertised cooldown out behind a live countdown and retries itself (75 s budget per search), the optional "falls verpasst" replans — one extra bahn.de call per tight transfer, the biggest multiplier on our upstream rate — are skipped while the circuit is open or the answer is stale and capped at 3 otherwise, and `/api/locations` degrades to an empty suggestion list instead of erroring mid-typing. Since 2026-08-21 the upstream client keeps **one live identity at a time** — one impersonation profile + one cookie jar + one connection, created and discarded as a unit — recycled after a jittered 50–100 requests or 600 s (`BAHN_SESSION_*`), so no single session accumulates enough history to be scored as one continuous heavy client; a 403 burns the whole identity and advances the profile rather than swapping the fingerprint in place on a session Akamai has already flagged, and a 429 still swaps nothing at all. Retired sessions close on a 30 s deferred timer (curl_cffi's `close()` is permanent and would kill in-flight requests), and `session_recycled` joins the `/health` counters. This replaced the old per-profile sessions held for the whole process lifetime, which had let 403 bursts recur overnight on 2026-08-20/21.

## Key implementation decisions

- **bahn.de web API instead of v6.db.transport.rest**: transport.rest (planned upstream) was down (503 on v5+v6) during development. bahn.de's own web API is what db-vendo wraps anyway; it returns Berlin-local naive times (no tz conversion) and ticket prices. See log.md 2026-07-12.
- **Arrival delay, not the dataset's `delay_in_min`**: the dataset's column prefers departure delay; passengers care about arrival. We compute `date_diff('minute', arrival_planned_time, arrival_change_time)` ourselves.
- **Delay score = final leg's median arrival delay** (delay at the destination), with worst-leg median as tiebreaker/transfer-risk signal (avg → median switched 2026-07-19).
- **Tight-transfer warning**: `tight_transfers()` in app/main.py flags transfers where the arriving leg's median delay leaves ≤ 2 min of buffer (`TRANSFER_TOLERANCE_MIN`); walking legs between trains are subtracted from the planned gap. Entries carry an `unlikely` flag (median delay > transfer time + 30 min, `UNLIKELY_EXCESS_MIN`) that switches the warning to "⛔ Unwahrscheinlicher Umstieg / Unlikely transfer", overrides the journey's headline badge with a red "⛔ Anschlussrisiko / Connection risk" pill (final-leg stats are meaningless if an earlier connection is missed), and demotes the journey in the least-delay sort (normal → unlikely → no data). Since 2026-07-26 a non-empty `tightTransfers` also puts a yellow "⚠ Knapper Umstieg / Tight transfer" pill in the journey header (tooltip lists the stations); it renders only when no transfer is unlikely, since the red pill replaces the median badge entirely. Next to the pill the median delay badge shows only when red (median ≥ 10 min); green/yellow/gray are suppressed, which also hides that card's badge-click day chart (2026-07-27). The header's badges, price, and booking button sit in a `.journey-cta` flex group so a too-narrow card wraps them together as a right-aligned block instead of orphaning the last item, and `.badge` carries an explicit line-height so emoji glyphs don't inflate pill height (2026-07-26). Below 700 px the header switches to a `1fr auto` grid with `.journey-cta { display: contents }` — times/price top row, badges right, full-width CTA bottom row — written against `.journey-head .price`/`.badge` so past mode (no `.journey-cta` wrapper) gets the same layout (2026-08-02).
- **EVA normalization**: dataset EVAs are 8-char zero-padded strings; bahn.de extIds are unpadded → `pad_eva()` in app/delays.py.
- **Window ends yesterday** by default: today's raw uploads (every 6 h) are incomplete.
- **Selectable averaging window (7/15/30 days)**: pipeline default is `--days 31` (30 full days, raw mirror ~4.5 GB at ~140 MB/day); `/api/journeys` takes `window` (Literal 7/15/30, default 7); `leg_delay_stats` filters `CAST(arrival_planned_time AS DATE) >= _max_day - (window-1)` — anchored to the newest day in the parquet, not now(), so stale data still yields full windows; cache keyed by `(train, eva, window)`. If the parquet holds fewer days than requested, results degrade gracefully (badge shows e.g. 7/30 Tage).
- **Site-wide DE/EN toggle (frontend only)**: header pills replace the chart-only toggle. Static text carries `data-i18n`/`data-i18n-placeholder`/`data-i18n-title` attributes; dynamic strings (status, badges, journey cards, tooltips) go through the `I18N` dict + `t()` in static/app.js. Status messages are stored as key+params so they re-render on switch; `<html lang>`, `document.title`, and the chart SVG (de/en variant) follow. Choice persists in localStorage. Data values (station names, prices, times) stay as the API returns them.
- **Automated daily refresh**: systemd timer `delaybahn-pipeline.timer` on ps083 runs the pipeline daily at 05:30 Europe/Berlin (`Persistent=true`, up to 15 min randomized delay), then restarts `delaybahn.service` to reload the parquet. `prune_old_raw_days()` in pipeline/build_delay_db.py removes raw-mirror days outside the window after each build, keeping `data/raw_data/` a rolling ~31 days.
- **Past-journey compensation checker (2026-07-23)**: `/api/journeys?mode=past` reuses the normal bahn.de search (works for past dates) and attaches per-leg `delayOnDate` (exact-day variant of the median lookup; `leg_delay_on_date`/`leg_departure_on_date` in app/delays.py). `_simulate_walk()` rides the journey with actual delays — a transfer is made only if the connecting train's actual departure (own delay included) leaves > 2 min — and on a miss/cancellation re-plans via bahn.de from that station to the destination (`_next_connection()` probes ready−45 min and picks the earliest actual arrival, so the just-ridden delayed train continuing onward is considered; ≤ 3 chained re-plans). Compensation (25 % ≥ 60 min / 50 % ≥ 120 min vs booked planned arrival) comes from the simulated arrival; the claim button opens a claim-steps modal (2026-07-31) whose continue link goes to bahn.de/buchung/reiseuebersicht/vergangene (account-based digital claim; Fahrgastrechte form fallback inside the modal). Frontend strikes out missed legs and renders the actually-taken continuation. Since 2026-08-14 replacements exclude FlixTrain (`_flix()` matches the BEF/Beförderer `zugattribut` now carried on `leg["line"]["operator"]`, `FLX` line-name prefix as fallback; whole itinerary dropped if any leg is Flix) — Flix runs its own tariff, so a stranded DB passenger cannot board one, and because it often arrives earliest it was displacing the real next connection and wiping out claims (visitor report).
- **Browser-fingerprint rotation + upstream cache (2026-07-25)**: Akamai blocks one curl_cffi `impersonate` profile at a time (chrome went 403 OPS_BLOCKED on 2026-07-23), so `app/bahn_api.py` holds a session per profile (`firefox135`, `safari17_0`, `chrome`) and rotates on a 403 before retrying. Locations (600 s) and journeys (300 s since 2026-08-13; was 120 s) are cached as shared asyncio tasks in a 512-entry LRU, so concurrent identical searches ride one upstream call (awaited through `asyncio.shield` since 2026-08-13, so one waiter's disconnect can't cancel the shared fetch); failed tasks are evicted so a block never sticks. Akamai also rate-limits per session cookie (429s during the 2026-08-13 surge, per-IP probes unaffected): journey departure times are floored to 5-min buckets before cache key + upstream body, and `_upstream_sem` bounds fan-out at 4 concurrent upstream requests. The morning's 429-triggered jar swap + profile rotation lasted one day — removed the same evening as rate-limit evasion; 429s feed the circuit breaker instead (below).
- **Live same-day delays from the DB Timetables API (2026-07-25)**: the batch design can only answer a journey the next morning (~06:20: HF publishes raw IRIS every 6 h, the build window ends yesterday, the timer fires 05:30). `app/live_delays.py` closes that by reading the delay at request time from IRIS `plan` (train number + planned time → stop id) + `fchg` (`ar/@ct`) — deliberately the *same field* the nightly build stores, so the number seen minutes after arrival is what the parquet will hold, and users never see it change. It is consulted only for days past `delays.coverage()[1]`, always with a parquet fallback, and an upstream failure degrades to "pending" instead of failing the search. A stop still in the future returns unknown rather than on time, since IRIS's silence is only punctuality once the stop is behind us. `warm()` prefetches an itinerary's stations concurrently so the per-leg lookups stay sync and `normalize_leg` stays unchanged in shape. Measured lookback 14–17 h, which overlaps the 06:20 build — so no intraday rebuild is needed. Credentials optional: without them the path is inert.
- **Local station autocomplete (2026-07-25)**: `/api/locations` answers from an in-memory index built from the parquet at startup (folded names collapse umlaut/Hbf spellings and multi-level EVAs; ranked prefix > word-start > substring, Hbf first, then observation volume), falling back to bahn.de only for stations with no delay history. Cuts the common keystroke path off the bot-protected upstream entirely.
- **Multi-country delay data (2026-07-20, AT 2026-08-14, NL+IT 2026-08-15)**: per-country producers emit the DE 17-column schema into `data/{at,nl,ch,fr,it}/days/*.parquet`; `merge_delays.py` unions them with a partition on the padded-eva country prefix (080/081/083/084/085/087) and a global last-midnight cut on both `time` and `arrival_planned_time` so no source shifts `_max_day`. CH: istdaten v2 (BPUIC == bahn.de extId; S-Bahn keyed by line digits because bahn.de sends the line, not the run number, for Swiss S-Bahn only). FR: SNCF GTFS-RT poller → `data/fr/obs.sqlite` (keep-last upsert) → daily consolidation; station IDs crosswalked SNCF-UIC → DB-EVA via committed `config/fr_uic_to_eva.json`; cancellations = trip CANCELED / stop SKIPPED, bare trip-cancellation markers propagated at consolidation. AT: ÖBB HAFAS (Scotty) ARR+DEP board poller over the ~200 busiest stations (`config/at_poll_stations.json`, ranked by ÖBB-GTFS rail stop events, ids resolved via bahn.de orte + board probing) → `data/at/obs.sqlite` → daily consolidation; the earlier "no per-stop open data" deferral was re-checked 2026-08-14 — ÖBB's new MMTIS CSVs are journey endpoints only, so board polling stayed the path. See log.md 2026-08-14. NL: OVapi train-only GTFS-RT poller, whole network in one 120 s fetch; train/station identity from OVapi's proto extension (`IFF:<type>:<number>` + IFF station code), so the daily rotation of OVapi's internal static-GTFS ids never touches the store; station codes crosswalked via committed `config/nl_stations.json` (Rijden de Treinen stations CSV; NL UIC codes are DB EVA numbers) → `data/nl/obs.sqlite` → daily consolidation; history seeded per-month from the Rijden de Treinen train archive (CC BY 4.0, credited in the footer). See log.md 2026-08-15. IT: ViaggiaTreno run tracking — 254 hub boards discover runs (both board types carry the andamentoTreno key triple), then each run is polled via `andamentoTreno`, which returns every stop's planned/actual times and cancellation flags in one call; station IDs crosswalked RFI-code → DB-EVA via committed `config/it_scode_to_eva.json` (trainline-eu seed + bahn.de orte, DB EVAs differ from Italian UIC like for FR). See log.md 2026-08-15.
- **German S-Bahn keyed by line label; untracked products gated (2026-08-02)**: the delays-table `train_no` is a CASE — DE `train_type='S'` rows (`eva LIKE '080%'`) key by `line_number` ("S5", bare digits get an "S" prefix) because bahn.de sends the line label as fahrtNr for German S-Bahn; all other rows keep `ltrim(train_number,'0')`. CH is fenced by EVA prefix (Swiss S-Bahn nummer is bare digits, already re-keyed in build_ch_days.py). Live IRIS path mirrors this: the plan parser keeps `ar/dp l`, and `_lookup` accepts a line match only for non-numeric query keys. `UNTRACKED_PRODUCTS` (BUS/TRAM/UBAHN/SCHIFF/ANRUFPFLICHTIG, blocklist so unknown products fail open) skips the lookup at all four consumption points and drives the frontend's "nicht erfasst" badge — also closes the latent false match of e.g. tram line "1" against train number 1. S-Bahn badge semantics: nearest run of the line within the ±120-min tolerance per day, the intended proxy for a headway service.
- **Pipeline deployed + day-incremental (2026-07-26)**: the 4-step `delaybahn-pipeline.service` (DE→CH→FR→merge, then app restart) and `delaybahn-fr-poller.service` are installed and enabled; the leftover session poller from 07-20 was killed. `build_delay_db.py` now parses raw XML once per day into a persistent `data/de/parsed/` cache and re-parses only days with new raw files, cutting the nightly run from ~40 min to minutes. `merge_delays.py` gained a symmetric lower window cut (`--window-days`, default 30) so the served parquet holds only days the app can serve and `/api/coverage` no longer advertises FR/CH-only days that are empty for DE journeys. See log.md 2026-07-26.
- **If-missed alternative behind tight-transfer warnings (2026-08-03)**: `_if_missed_connection()` in app/main.py fills `tt["ifMissed"]` for every tight transfer in future mode — the next realistic connection from the transfer station to the journey's destination, assuming the passenger is ready at planned arrival + the arriving leg's median delay (+ walk minutes); catchable = planned departure leaves > `TRANSFER_TOLERANCE_MIN` after that (excludes the missed train by definition), earliest planned arrival wins. Reuses the past-mode `_replan` helper via one `asyncio.gather` after journey assembly (one deduped bahn.de call per tight transfer); `tight_transfers()` entries now carry `depLegIndex`. Frontend renders it as a disclosure button on the warning strip; open panels cross out the legs from the missed departure onward (earliest open miss wins) via the past-mode `.leg-missed` style. Skips FlixTrain candidates since 2026-08-14, same rule and same reason as the past-mode replan.
- **Risk sort ranks within tiers by `minTransferMargin` (2026-07-26)**: min(transfer time − arriving leg's median delay) over *all* train-to-train transfers, computed server-side with the same `_transfer_pairs` helper as the tight-transfer detection; the risk sort orders each pill tier by that slack descending (direct journeys first, no-data journeys last). See log.md 2026-07-26.

- **Echtzeit passed only where it deviates (2026-08-03)**: `normalize_leg` sets `departure`/`arrival` (and `journeys` sets `ezDurationSeconds`) only when the live value differs from the planned one, so their absence keeps meaning "on schedule" and the frontend needs no on-time special case. `_transfer_pairs` prefers live times over the schedule for the gap; past mode ignores the live fields entirely.
- **Past mode on its own sub-page, served by rewriting index.html (2026-08-03)**: `/entschaedigung` is a FastAPI route that regex-rewrites `static/index.html` per request (`_past_page_html()`) — head tags, `body.past-mode`, banner `<strong>`→`<h1>` — instead of a second HTML file, so homepage edits can never leave the sub-page stale. The path decides the frontend mode; `setMode()` is gone and mode-entry links are real `<a>`s, which makes the page crawlable and drops the `?mode=past` state from URLs (legacy links redirect client-side).

- **Stale fallback + overload UX (2026-08-13)**: `bahn_api.journeys` returns `(data, stale_age_seconds)` — successful fetches are remembered (256-entry LRU, ≤ 1 h, stamped at fetch completion so the age is honest) and served with their age when bahn.de refuses; `/api/journeys` marks them `staleSeconds` and `Cache-Control: no-store` so no cache pins a degraded copy. The frontend auto-retries a 429/502/503/504 exactly once after 4.5 s behind a non-error "überlastet" status (search + paging), fails to a friendly bilingual message, and renders stale results behind an amber notice strip that re-renders on language switch. Upstream 429s feed a rolling 5-min counter; ≥ 8 fires one ntfy alert per 30 min (same NTFY_TOPIC/NTFY_URL as feedback).
- **Wait the cooldown out client-side rather than failing (2026-08-13)**: the server knows exactly how long bahn.de wants us to pause and already sends it as `Retry-After` on the 503, so the browser honours that number — a live countdown in the status line, then an automatic retry, up to 75 s per search (`RETRY_MAX_TOTAL_S`, 60 s per single wait, 8 s when the header is missing). A `searchGen` counter supersedes a countdown the user walked away from, so the abandoned fetch renders nothing and does not re-enable the newer search's button. Rationale: bahn.de's windows are ~45 s and users tolerate that far better than "try again later"; the previous fixed 4.5 s retry was inside the cooldown by construction and could only fail. The breaker's own escalation was corrected at the same time — a named `Retry-After` is authoritative and used verbatim (capped), never max'd against the doubling ladder, which would otherwise have turned a 45 s ask into a 300 s blackout after a few opens. Since 2026-08-17 only the first countdown uses the plain "überlastet" wording; every later round switches to a numbered variant ("DB-Server weiterhin überlastet – 2. Versuch in …" / "DB's servers are still busy – retry 2 in …"), so a second countdown no longer reads as the first one looping.
- **Optional enrichment yields to the searches users wait on (2026-08-13)**: `_if_missed_connection` costs one extra bahn.de call per tight transfer per search — the largest multiplier on our upstream rate — for a disclosure most readers never open. It is skipped when `bahn_api.healthy()` is false or the answer is already stale, and capped at `BAHN_MAX_IF_MISSED_REPLANS` (3); the tight-transfer warning itself is unaffected, and the frontend already treated a missing `ifMissed` as "nothing to disclose". `/api/locations` follows the same principle in reverse: a failed suggestion lookup returns `[]` rather than an error, since the local station index already answers everything with delay data.
- **Circuit breaker + per-IP limits instead of identity rotation (2026-08-13)**: bahn.de failures are a typed taxonomy (`UpstreamRateLimited/Blocked/Unavailable/ProtocolError`) raised by `bahn_api._request`, which runs every call through a `CircuitBreaker` (threshold 5/60 s; cooldown 30 s → 300 s cap, doubling + jitter; `Retry-After` in delta or HTTP-date form respected up to the cap and opening immediately; 1 half-open probe; 403-wholesale force-opens 30 s). The only 429 retry is one same-session wait when `Retry-After` ≤ 2 s — never a new jar or profile, which would be rate-limit evasion. `app/main.py` maps the taxonomy to 503 + `Retry-After` (throttle/outage, after the stale fallback), 502 (unusable response) and keeps our own 429 for clients over the per-IP search budget (`app/ratelimit.py`: burst 10/10 s + 40/min sliding windows, IP from `cf-connecting-ip` — trustworthy since the origin is only reachable through the Cloudflare tunnel — rejected attempts uncounted so limited clients recover). Counters + circuit state ride `/health`; knobs are env vars via `app/config.py` (`BAHN_*`, `CLIENT_SEARCH_*`); everything is per-process, matching the single-worker deployment.
- **A round trip is only shown once both halves exist (2026-08-13)**: step 2 used to run after the user had picked an outbound, so a throttled bahn.de surfaced as a dead end two steps in — or, until the same day's skew bound, as connections for an entirely different time of day. `runSearch()` now calls `preflightReturn()` before rendering the outbound list; `fetchJourneys(pagingRef, opts)` takes `{leg, maxTotal, retryStatusKey, retryAgainStatusKey}` so that probe can fetch the reverse direction with a longer budget (150 s vs 75 s — abandoning it wastes an outbound answer already paid for) and name which half is missing. The proven payload rides `state.returnPrefetch` into step 2 and is reused when its departure string still matches, so the guarantee costs one upstream call, not two; it is dropped on a new search and on any window/D-Ticket refetch. A probe that legitimately returns zero connections counts as answerable — retrying there would never terminate.
- **PWA offline strategy (2026-08-10)**: `static/sw.js` precaches the app shell and serves it cache-first (background revalidate), but every `/api/*` response is network-first and stamped with an `sw-cached-at` header; the offline fallback serves a cached delay response only if it is younger than 10 min (`API_MAX_AGE`), else 503 — the app must never show stale delay data. The precache list pins the current `?v=` cache-busters, so a buster bump must bump `SHELL_VERSION` and the pinned URLs together to drop old shells. Non-GET (the feedback POST), `/stats`, `/health` and redirects are deliberately not cached. `sw.js` has a fixed URL that can't be `?v=`-busted, so an explicit `/sw.js` route (app/main.py, 2026-08-11) serves it with `Cache-Control: no-cache` — otherwise Cloudflare edge-caches it (~4 h) and a new `SHELL_VERSION` can't roll out. The HTML documents have the same unbustable-URL problem, and since 2026-08-15 the mount is a `HtmlNoCacheStatic` subclass that stamps `Cache-Control: no-cache` on any `text/html` response (`/entschaedigung` sets it on its own `HTMLResponse`): without it `StaticFiles` sent only a `Last-Modified`, and browsers' heuristic freshness (~10 % of the document's age) served a weeks-old homepage — which is how a user hit a page still missing the 2026-07-28 footer disclaimer. `no-cache` forces revalidation, not re-download; `Last-Modified` still yields 304s, and the versioned assets are untouched.
- **Walk legs name their duration (2026-08-14)**: walk rows render "Fußweg · 7 min · A → B" from the leg's own `plannedDeparture`/`plannedArrival`, which the payload always carried and the renderer used to drop. It exists to explain the tight-transfer figure: `_transfer_pairs` subtracts the walk from the arrival→departure gap, so a 23:25 arrival and a 23:32 departure legitimately warn "0 min", and until now nothing on the card accounted for the missing seven minutes. The transfer sentence itself was deliberately left alone. `node --check` only — not browser-verified.
- **Install prompt on every installable browser (2026-08-11, desktop added 2026-08-14)**: `beforeinstallprompt` drives an in-page Install button on Android *and* desktop Chromium; `navigator.userAgentData.mobile` (UA `/android|mobile/` fallback) no longer gates the banner, only the lead wording — "vom Startbildschirm" is a phone sentence, so desktop points at the phone instead: "Öffne delaybahn.com im Browser deines Handys und tippe auf „Installieren“." (`installLeadDesktop`, swapped via `dataset.i18n` so a DE/EN toggle keeps it) — and the `track("install")` platform. Desktop keeps the omnibox install icon as well; `preventDefault()` only suppresses the mobile mini-infobar. iOS, where no browser has an install API, shows the same Install button; tapping it opens a bottom sheet (`<dialog>`) with the 3-step Share → Add-to-Home-Screen instructions (2026-08-11). Until 2026-08-22 that path was gated on Safari alone (`isIOSSafari`, excluding `crios|fxios|edgios`), so iOS Chrome/Firefox/Edge fell through to the Chromium branch and, since no iOS browser ever fires `beforeinstallprompt`, saw no banner at all. An `iosBrowser` discriminator replaced it: every iOS browser gets the sheet, and its lead swaps to `iosSheetLeadChrome` or the generic `iosSheetLeadOther` via `dataset.i18n`. Chrome also gets its own steps 1–2 (`iosStep1Chrome`/`iosStep2Chrome`), because Safari's wording actively misleads there — Chrome's ⋯ overflow menu ends in a "Share Chrome" item that shares the App Store listing rather than the page, so the sheet names the address-bar share icon ("next to the website name") and says to scroll, the Add-to-Home-Screen row sitting near the bottom of the share sheet's action list. Third-party iOS browsers have been able to add a real standalone home-screen web app since iOS 16.4, and the manifest's `display: standalone` is what makes the icon launch in its own WebView rather than opening the default browser; `track("install")` now carries `browser` so the Chrome-iOS funnel is separable. Dismissal (✕), `appinstalled`, and an already-standalone launch suppress it (`installPromptDismissed`, 60-day re-arm). The app icons are the DelayBahn logo's train mark (DB-clock monogram in a train silhouette, since 2026-08-13; previously the boxed monogram), white on red, derived from `logo.png` by cropping the mark above the wordmark and thresholding its ink to a solid mask, the DB glyphs kept at the earlier icons' size for legibility.
