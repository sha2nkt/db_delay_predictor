## 2026-07-25 — bahn.de fingerprint rotation + upstream request cache

- On 2026-07-23 Akamai Bot Manager started answering every `impersonate="chrome"` profile with 403 OPS_BLOCKED (fresh sessions blocked too, so it was the TLS/HTTP2 fingerprint, not cookies or rate); firefox and safari profiles passed. `app/bahn_api.py` now keeps a `PROFILES` list (`firefox135`, `safari17_0`, `chrome`) with one lazily-built `AsyncSession` each and rotates to the next profile on a 403, retrying the same request (`_request()`); the rotation is guarded by a lock so concurrent 403s advance the index once. `client` is gone — `app/main.py` shuts down via the new `bahn_api.close()`.
- Both upstream calls go through `_cached()`: an LRU (`CACHE_MAX=512`) of asyncio tasks keyed by the request arguments, TTL 120 s for journeys and 600 s for locations. Callers await the shared task, so a spike on the same search rides one upstream request; a still-running task is handed out even past its TTL. Failed or cancelled tasks are dropped from the cache in a done-callback, so a block clears as soon as the next request rotates.

## 2026-07-27 — Load-test harness; DuckDB lookups made sargable; caches bounded

- **Why**: the app had never been load tested, and three properties made a naive test useless or harmful — one uvicorn worker with no uvloop/httptools, blocking `_conn.execute()` calls inside `async def` handlers, and `/api/journeys` depending on bahn.de (an unofficial Akamai-protected API whose 403 path retries all three impersonation profiles, so a burst triples outbound requests exactly when a ban is likeliest).
- **Harness** (`pipeline/loadtest.py`, `pipeline/loadtest_stub.py`, artifacts in gitignored `data/loadtest/`). The stub serves the real `app.main` with three network boundaries rebound — `bahn_api._request`, `live_delays._get_xml` (plus `configured()` forced false), and the Umami `httpx.AsyncClient` via `MockTransport` — so the LRUs, TTLs, single-flight task sharing and the IRIS semaphore all still execute while nothing leaves the box and no analytics rows are written. Fixtures came from one `--record` pass (~25 real bahn.de calls, 6 high-transfer routes × future/past, 5–9 journeys of 1–6 legs each). Unknown request keys fall back deterministically rather than erroring, so `_simulate_walk` still recurses to `MAX_REPLANS`. The driver models sessions from `static/app.js` (page load, 250 ms-debounced autocomplete, search, 12 % window switch, 10 % paging, 8 % past mode, 15 % chart toggle ≈ 10.7 requests/session), uses open-loop Poisson arrivals so saturation shows as a queue rather than client self-throttling, samples `/proc/<pid>` at 1 Hz, and runs a 2 rps `/api/coverage` canary whose p99 is a direct read of event-loop block time. Only 12 fixtures exist, so their trains warm `delays._cache` within seconds and a plain run measures a warm cache; `--unique-routes` tags each session with a variant that swaps every leg's train for a different real train calling at that station **in the same hour** (hour-bucketed so the query's `tod_diff <= 120` filter still matches and stats stay truthful), keeping keys cold.
- **Baseline** (cold caches, 2/5/10 sessions per second): 156–199 % CPU of one core, canary p99 100–152 ms, static-asset p99 113–158 ms. The event loop was blocked long before the box was busy.
- **Root cause**: `ltrim(train_number, '0') = ?` is not sargable, so every leg lookup scanned all 19.5M rows — 6.4 ms wall across 32 threads but ~110 ms of core time, and a journey response does ~30 lookups. The table is now built with a materialized `train_no` column and `ORDER BY train_no, eva`, which lets zone maps skip row groups: 1.24 ms single-threaded, and `SET threads=4` since the fan-out is no longer needed. Startup grows ~1 s to ~5 s (widens the nightly restart window by the same amount).
- **After** at the same three rates: 4.9/9.1/13.6 % CPU, canary p99 5.6/5.2/16.1 ms, static p99 ~20 ms. 30-minute soak at 10 sessions/s: 185 899 requests, 0 errors, 10.4 % CPU, RSS +11.8 MB (0.32 MB/min), canary p99 3.9 ms.
- **Equivalence checked before trusting the rewrite**: 400 sampled real `(train, eva, time-of-day)` triples through both schemas showed 4 mismatches — not from the rewrite, but because `DISTINCT ON (day) ... ORDER BY day, tod_diff` ties for frequent services (train 5 at one station has 2944 stops in 30 days) and the winner depended on physical row order, so results could shift on any nightly rebuild. Added `arrival_planned_time, arrival_change_time` (and the departure equivalents) as explicit tie-breaks; re-ran → 0/754 mismatches.
- **Caches bounded**: `delays._cache`, `_date_cache`, `_dep_date_cache` were never evicted at all and `main._replan_cache` held raw bahn.de payloads (100–500 KB each) up to 5000 entries before a wholesale `clear()` — ~1–2 GB of transient growth on a ~6 GB process. All four are now `OrderedDict` with LRU eviction reusing the `bahn_api._cached` pattern (50 000 / 500 caps); eviction and LRU-vs-FIFO behaviour asserted directly.
- **Also**: `/health` (registered before the `StaticFiles` mount, which is last and would otherwise swallow it) returning row count and the five cache sizes — a permanent loop canary and uptime probe; a 403 circuit breaker in `bahn_api` (`_blocked_until`, 30 s) so a wholesale Akamai block fails fast instead of tripling outbound rate; `uvicorn[standard]` in pyproject (uvloop + httptools) — **recorded but not synced**, since the venv is shared with the running service.
- **Not done**: Cloudflare cache rules (`/` sends no `Cache-Control` and is `cf-cache-status: DYNAMIC`, i.e. every homepage load reaches the origin; the existing `Cache /api/*` rule reports `BYPASS` and appears not to be caching), `--limit-concurrency` on the unit, `Cache-Control` on versioned static assets, rounding `departure` to 10-minute buckets to give `/api/journeys` a usable edge hit rate. `delays._cache`'s key still omits time-of-day while the SQL filters on it — a real correctness bug, untouched here.

- Robustness (from review): `init()` falls back on the *open failing*, not just the file missing — a truncated db or a duckdb up/downgrade that can't read the format serves stale-but-working parquet instead of a restart loop (which systemd OnFailure alerts can't see). The db is built from the *staged* parquet before either file is swapped in, so a failed build leaves parquet+db consistent (both old). Staging name is `.building`, not `.tmp` — `<db>.tmp` is DuckDB's own default temp_directory for the target db and a spill would turn the staging path into a directory. The build sets `threads=4` + `memory_limit=2GB` (2.5 G peak vs 4 G unbounded on the 32-core dev box) and re-opens the staged file read-only with a row-count + `reason_code` probe so a bad build fails the 05:30 pipeline run (alerted via ntfy OnFailure) rather than the app restart after it. duckdb deliberately not pinned exactly: newer duckdb reads older files, uv.lock freezes the version in practice, and the fallback covers the downgrade case.
- Benchmarked on production hardware (185 real sampled keys, live app running): build 37.9 s; init 0.6–0.8 s (was ~45 s); first-touch queries p50 13.8 / p95 24.4 ms after a forced OS-cache drop, DuckDB-warm p50 7–8 ms; RSS ~470 MB (was 4.1 G steady / 6.7 G peak). On ps083 (same-hardware comparison) file-backed matched in-memory: p50 1.1 vs 1.5 ms. Per-leg cost is invisible next to the 2–5 s bahn.de call (~30 lookups/search ⇒ ≤ 0.3 s worst-case cold). Correctness: 189/190 keys byte-identical between modes; the one diff is a single day's `reason` annotation on an S-Bahn key where duplicate observations tie on every sort key — physical-order nondeterminism that already exists between two in-memory startups. Corrupt-db fallback verified (garbage file → parquet load, 19.5 M rows served).

## 2026-08-13 — Round trip showed afternoon return connections for a 22:00 return; gate the outbound list on the return leg

- Symptom (visitor feedback): a same-day Frankfurt Airport → Düsseldorf Hbf round trip with the return set to 22:00 listed return connections from 17:06 and 18:21, and "later connections" then failed with "DB-Server überlastet". The reporter guessed a delaybahn↔DB problem, which was right.
- Root cause: the route-level stale index added this morning matched on `(from, to, dticket)` plus the *calendar day* only (`r[1][:10] == departure_iso[:10]`), never the time of day. With bahn.de refusing, a 22:00 return search was answered from any ≤ 1 h-old successful search for that route on that date — in this case someone's afternoon one. The staleness notice says "Ergebnisse vom Stand vor X Min.", which explains the fetch age but not a five-hour window shift, so it reads as the site ignoring the entered time. Paging then had no fallback at all (paged responses are deliberately kept out of the route index), so "later" surfaced the raw 503. Confirmed in production: 569 route-match serves in the day's journal, including this exact leg (`Düsseldorf Hbf -> Frankfurt(M)Flughafen` at 12:25 and 12:41), and `/health` showing `stale_hits_route` 334 vs `stale_hits` 17 — the loose fallback fires ~20× more often than the exact-key one, and every one of those could answer a different time window.
- Fix, on the user's design call ("only show the onward journey if the return trip at the right time is pollable; if not, keep trying"): the round trip now preflights. `runSearch()` fetches the outbound, then — before rendering anything — `preflightReturn()` (static/app.js) searches the return direction at the requested time. Only when that lands does step 1 appear; the proven payload is kept in `state.returnPrefetch` and handed to step 2, so picking an outbound costs no second upstream call unless the return was clamped up to the outbound arrival or the return fields were edited meanwhile (departure-string compare). `fetchJourneys` grew a second `opts` argument (`leg`, `maxTotal`, `retryStatusKey`) so the preflight can fetch a leg other than the one on screen with its own budget and wording: 150 s (`PREFLIGHT_MAX_TOTAL_S`) against a plain search's 75 s, because giving up throws away an outbound answer the user is already waiting on. New strings `returnChecking` / `returnRetryIn` / `returnUnavailable` in both languages name which half is missing, instead of the generic overload message.
- Fix, backend: the route fallback additionally requires the remembered departure within `STALE_ROUTE_MAX_SKEW` (`BAHN_STALE_ROUTE_SKEW_SECONDS`, 1800 s) of the one asked for (`_departure_skew`, inf on an unparsable value). It still covers what it was built for — 5-minute bucket rollover on "now" searches — but can no longer stand in for another time of day. Without this the preflight could be "satisfied" by exactly the wrong-window answer that caused the report.
- Also: the client's retry wait now has a 1 s floor. A `Retry-After: 0` would have spun the loop without ever consuming the budget — unreachable today (both our own limiter and `_upstream_http_error` floor at 1) but a hot loop if an upstream ever sent it.
- Busters: app.js v=81; sw.js `SHELL_VERSION` v10 with the precache pins updated, including `style.css?v=59` → `v=60`, which had drifted from index.html and was precaching a URL the page never requests.
- Verified — unit (58 pass): a 17:00 answer no longer serves a 22:00 query while the 30-min bucket-rollover case still does. Real Chrome via Playwright against the worktree app on live bahn.de: the happy path issues exactly two `/api/journeys` calls (outbound 09:00, return 22:00 reversed), clicking "Weiter" issues **none**, and the return list starts 23:01 — the requested window. With the return leg 503ing twice (injected `Retry-After: 2`): `#results` empty, zero "Weiter" buttons, status "Rückfahrt noch nicht abrufbar – neuer Versuch in 2 s…", then the outbound list appears once the return recovers. Note for future browser tests: the service worker owns `/api/*`, so page-level `route()` interception needs a context with `serviceWorkers: "block"`.
- Deliberate: a return probe that succeeds with zero connections counts as pollable (the outbound still shows) — retrying there would spin forever on a legitimately empty result; and an in-window stale answer still counts, with the existing age notice. Only the wrong-window case is refused now.

## 2026-08-13 — Track earlier/later paging clicks; prefetching them is not worth the upstream cost yet

- Question raised: could a few pages before and after be bundled into one bahn.de request, so paging doesn't wait? No. `/angebote/fahrplan` answers with one page (~6-7 connections) plus two opaque cursors in `verbindungReference`; paging means re-POSTing the same body with `pagingReference`, and the body — which mirrors bahn.de's own search mask — has no count, window or page-span field. bahn.de's own site pages click-by-click the same way. It is an undocumented private API, so a hidden knob can't be ruled out without probing, which isn't worth spending on a throttled upstream.
- Prefetching would give the same effect, but the measured payoff doesn't justify it yet: 32 694 `/api/journeys` requests in 24 h, 3 467 of them carrying a `pagingRef` (both figures include client retries) — roughly 12 paging clicks per 100 searches. Prefetching earlier+later after every search would add up to 2 upstream searches per search, roughly tripling bahn.de search volume to serve under 12 % of them, on the exact budget that caused the 2026-08-13 outage. Recorded as a next candidate with the cheaper shape: prefetch on `pointerenter`/`touchstart` (intent-triggered, so cost tracks clicks not searches), deduped against the click and gated on `bahn_api.healthy()` like the if-missed replans.
- Shipped instead, on user instruction ("track paging in umami but nothing else"): `loadPage()` emits `track("page", {dir, leg})`. Placed after the `!ref` early return but before the fetch, so it counts intent — a page that fails upstream is still a user who wanted one. `leg` separates one-way paging from round-trip outbound/return, which the server-log ratio above cannot; past vs future is already separable by page URL in Umami.
- Busters: app.js v=82; sw.js `SHELL_VERSION` v11 with the precache pin updated.
- Verified in real Chrome (Playwright, live bahn.de, `window.umami` stubbed via `addInitScript` since /stats 502s on the dev box): "Spätere" emitted `{dir:"later", leg:"outbound"}`, "Frühere" emitted `{dir:"earlier", leg:"outbound"}`, and no event fires when the direction has no cursor.
- Found while testing, not fixed (out of the "nothing else" scope): the station suggestion list can re-open *after* the field is left. The dropdown closes 150 ms after blur, but a `/api/locations` response resolving later calls `toggle("open", items.length > 0)` unconditionally, so a fast typist can be left with suggestions floating over the results — it was covering the "Frühere Verbindungen" button in the test run, which is also why browser tests here need the field re-focused and blurred before clicking page buttons.
