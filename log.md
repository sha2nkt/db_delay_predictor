## 2026-07-25 — bahn.de fingerprint rotation + upstream request cache

- On 2026-07-23 Akamai Bot Manager started answering every `impersonate="chrome"` profile with 403 OPS_BLOCKED (fresh sessions blocked too, so it was the TLS/HTTP2 fingerprint, not cookies or rate); firefox and safari profiles passed. `app/bahn_api.py` now keeps a `PROFILES` list (`firefox135`, `safari17_0`, `chrome`) with one lazily-built `AsyncSession` each and rotates to the next profile on a 403, retrying the same request (`_request()`); the rotation is guarded by a lock so concurrent 403s advance the index once. `client` is gone — `app/main.py` shuts down via the new `bahn_api.close()`.
- Both upstream calls go through `_cached()`: an LRU (`CACHE_MAX=512`) of asyncio tasks keyed by the request arguments, TTL 120 s for journeys and 600 s for locations. Callers await the shared task, so a spike on the same search rides one upstream request; a still-running task is handed out even past its TTL. Failed or cancelled tasks are dropped from the cache in a done-callback, so a block clears as soon as the next request rotates.

## 2026-07-27 — Load-test harness; DuckDB lookups made sargable; caches bounded

- **Why**: the app had never been load tested, and three properties made a naive test useless or harmful — one uvicorn worker with no uvloop/httptools, blocking `_conn.execute()` calls inside `async def` handlers, and `/api/journeys` depending on bahn.de (an unofficial Akamai-protected API whose 403 path retries all three impersonation profiles, so a burst triples outbound requests exactly when a ban is likeliest).
- **Harness** (`pipeline/loadtest.py`, `pipeline/loadtest_stub.py`, artifacts in gitignored `data/loadtest/`). The stub serves the real `app.main` with three network boundaries rebound — `bahn_api._request`, `live_delays._get_xml` (plus `configured()` forced false), and the Umami `httpx.AsyncClient` via `MockTransport` — so the LRUs, TTLs, single-flight task sharing and the IRIS semaphore all still execute while nothing leaves the box and no analytics rows are written. Fixtures came from one `--record` pass (~25 real bahn.de calls, 6 high-transfer routes × future/past, 5–9 journeys of 1–6 legs each). Unknown request keys fall back deterministically rather than erroring, so `_simulate_walk` still recurses to `MAX_REPLANS`. The driver models sessions from `static/app.js` (page load, 250 ms-debounced autocomplete, search, 12 % window switch, 10 % paging, 8 % past mode, 15 % chart toggle ≈ 10.7 requests/session), uses open-loop Poisson arrivals so saturation shows as a queue rather than client self-throttling, samples `/proc/<pid>` at 1 Hz, and runs a 2 rps `/api/coverage` canary whose p99 is a direct read of event-loop block time. Only 12 fixtures exist, so their trains warm `delays._cache` within seconds and a plain run measures a warm cache; `--unique-routes` tags each session with a variant that swaps every leg's train for a different real train calling at that station **in the same hour** (hour-bucketed so the query's `tod_diff <= 120` filter still matches and stats stay truthful), keeping keys cold.
- **Baseline** (cold caches, 2/5/10 sessions per second): 156–199 % CPU of one core, canary p99 100–152 ms, static-asset p99 113–158 ms. The event loop was blocked long before the box was busy.
- **Root cause**: `ltrim(train_number, '0') = ?` is not sargable, so every leg lookup scanned all 19.5M rows — 6.4 ms wall across 32 threads but ~110 ms of core time, and a journey response does ~30 lookups. The table is now built with a materialized `train_no` column and `ORDER BY train_no, eva`, which lets zone maps skip row groups: 1.24 ms single-threaded, and `SET threads=4` since the fan-out is no longer needed. Startup grows ~1 s to ~5 s (widens the nightly restart window by the same amount).
- **After** at the same three rates: 4.9/9.1/13.6 % CPU, canary p99 5.6/5.2/16.1 ms, static p99 ~20 ms. 30-minute soak at 10 sessions/s: 185 899 requests, 0 errors, 10.4 % CPU, RSS +11.8 MB (0.32 MB/min), canary p99 3.9 ms.
- **Equivalence checked before trusting the rewrite**: 400 sampled real `(train, eva, time-of-day)` triples through both schemas showed 4 mismatches — not from the rewrite, but because `DISTINCT ON (day) ... ORDER BY day, tod_diff` ties for frequent services (train 5 at one station has 2944 stops in 30 days) and the winner depended on physical row order, so results could shift on any nightly rebuild. Added `arrival_planned_time, arrival_change_time` (and the departure equivalents) as explicit tie-breaks; re-ran → 0/754 mismatches.
- **Caches bounded**: `delays._cache`, `_date_cache`, `_dep_date_cache` were never evicted at all and `main._replan_cache` held raw bahn.de payloads (100–500 KB each) up to 5000 entries before a wholesale `clear()` — ~1–2 GB of transient growth on a ~6 GB process. All four are now `OrderedDict` with LRU eviction reusing the `bahn_api._cached` pattern (50 000 / 500 caps); eviction and LRU-vs-FIFO behaviour asserted directly.
- **Also**: `/health` (registered before the `StaticFiles` mount, which is last and would otherwise swallow it) returning row count and the five cache sizes — a permanent loop canary and uptime probe; a 403 circuit breaker in `bahn_api` (`_blocked_until`, 30 s) so a wholesale Akamai block fails fast instead of tripling outbound rate; `uvicorn[standard]` in pyproject (uvloop + httptools) — **recorded but not synced**, since the venv is shared with the running service.
- **Not done**: Cloudflare cache rules (`/` sends no `Cache-Control` and is `cf-cache-status: DYNAMIC`, i.e. every homepage load reaches the origin; the existing `Cache /api/*` rule reports `BYPASS` and appears not to be caching), `--limit-concurrency` on the unit, `Cache-Control` on versioned static assets, rounding `departure` to 10-minute buckets to give `/api/journeys` a usable edge hit rate. `delays._cache`'s key still omits time-of-day while the SQL filters on it — a real correctness bug, untouched here.

- Robustness (from review): `init()` falls back on the *open failing*, not just the file missing — a truncated db or a duckdb up/downgrade that can't read the format serves stale-but-working parquet instead of a restart loop (which systemd OnFailure alerts can't see). The db is built from the *staged* parquet before either file is swapped in, so a failed build leaves parquet+db consistent (both old). Staging name is `.building`, not `.tmp` — `<db>.tmp` is DuckDB's own default temp_directory for the target db and a spill would turn the staging path into a directory. The build sets `threads=4` + `memory_limit=2GB` (2.5 G peak vs 4 G unbounded on the 32-core dev box) and re-opens the staged file read-only with a row-count + `reason_code` probe so a bad build fails the 05:30 pipeline run (alerted via ntfy OnFailure) rather than the app restart after it. duckdb deliberately not pinned exactly: newer duckdb reads older files, uv.lock freezes the version in practice, and the fallback covers the downgrade case.
- Benchmarked on production hardware (185 real sampled keys, live app running): build 37.9 s; init 0.6–0.8 s (was ~45 s); first-touch queries p50 13.8 / p95 24.4 ms after a forced OS-cache drop, DuckDB-warm p50 7–8 ms; RSS ~470 MB (was 4.1 G steady / 6.7 G peak). On ps083 (same-hardware comparison) file-backed matched in-memory: p50 1.1 vs 1.5 ms. Per-leg cost is invisible next to the 2–5 s bahn.de call (~30 lookups/search ⇒ ≤ 0.3 s worst-case cold). Correctness: 189/190 keys byte-identical between modes; the one diff is a single day's `reason` annotation on an S-Bahn key where duplicate observations tie on every sort key — physical-order nondeterminism that already exists between two in-memory startups. Corrupt-db fallback verified (garbage file → parquet load, 19.5 M rows served).

## 2026-08-15 — Dutch delay coverage via OVapi GTFS-RT, seeded from the Rijden de Treinen archive

- Source decision: two-part. The rolling window comes from OVapi's train-only GTFS-RT feed (`https://gtfs.ovapi.nl/nl/trainUpdates.pb`, ~1.8 MB, no key, whole country in one request — the FR mold, not the AT one); history is seeded from the Rijden de Treinen train archive (monthly CSV.gz of every passenger stop since 2019, CC BY 4.0, published ~4 days after month end). The official NS API was rejected (rate limits deliberately tightened for non-private use, and a station-board pattern costs hundreds of requests per sweep for the same numbers); raw NDOV streams rejected (ZeroMQ + ARI XML, far more engineering for identical data — OVapi and Rijden de Treinen both sit on those streams already).
- The load-bearing feed discovery: OVapi's proto extension (field 1003) carries `realtime_trip_id` `IFF:<type>:<number>` on every TripDescriptor and the IFF station code (+ scheduled/actual track) on every StopTimeUpdate. - Root cause: `StaticFiles` sends the HTML documents with a `Last-Modified` but no `Cache-Control` and no `ETag`, and `index.html` has no `?v=` buster of its own (only its subresources do, and they are what the buster discipline covers). With no explicit freshness, browsers fall back to heuristic caching (RFC 9111 §4.2.2, commonly 10 % of the time since `Last-Modified`), so the longer the homepage went untouched the longer a stale copy was reused without revalidating — a file last modified 20 days ago reads as fresh for ~2 days. Cloudflare was not involved (`cf-cache-status: DYNAMIC`), and the service worker was not either (navigations are network-first; its shell copy is an offline fallback). The platform-dependence was an artefact of when each browser profile last fetched the page relative to a deploy.
- Fix: `HtmlNoCacheStatic`, a `StaticFiles` subclass overriding `file_response` — the single funnel every file the mount serves passes through — to set `Cache-Control: no-cache` when the response's `media_type` is `text/html`. That covers `/`, `/index.html` and `/impressum.html` without enumerating routes and picks up any HTML added later, while `style.css`, `app.js` and the SVGs keep no `Cache-Control` at all and stay on the long-cache + `?v=` scheme. Args are forwarded as `*args/**kwargs` because Starlette has moved that signature across versions. `/entschaedigung` is a hand-built `HTMLResponse` that never passes through the mount, so it carries the header directly.
- `no-cache` means revalidate-before-reuse, not don't-store: `StaticFiles` still emits `Last-Modified`, so an unchanged page answers 304 with an empty body — a conditional request per navigation rather than the ~30 KB document. `no-store` was rejected (full re-download every navigation, and it disables the back/forward cache); a short `max-age` was rejected because it leaves the same class of bug with a bounded window instead of an unbounded one. This is the same treatment `/sw.js` has had since 2026-08-11, for the same reason: a URL that can never be busted must be revalidated.
- Verified with `TestClient` against the real app: `/`, `/entschaedigung` and `/impressum.html` come back `Cache-Control: no-cache`; `style.css` and `app.js` come back with none (busters intact); `/sw.js` unchanged; a conditional GET on `/` with the served `Last-Modified` still answers 304, so revalidation stays cheap.
- Busters: none. Backend-only change, nothing under `static/` touched, so no `?v=` move and no `SHELL_VERSION` bump — app.js stays v=89, style.css v=64, sw.js v22.
- Residual: the header only governs responses from this deploy onward. A browser already holding a heuristically-fresh copy keeps it until that window expires or the user hard-reloads; nothing server-side can recall it.

## 2026-08-20 — Cache the if-missed answer instead of the payload it came from, and log real upstream volume

- User ask: how often does bahn.de 429 us on the new Hetzner box, can heavier caching make it rare, and what are the pros and cons of heavy caching. Answered by measurement rather than by tuning knobs; the measurements then killed two of the three mitigations proposed in the first pass, and this entry records both what shipped and what was rejected, since the rejections are the reusable result.
- Frequency, from the full journal on delaybahn_hetzner2 (log begins 08-19 15:33, the move): **917 429s over 17.2 h**, ~51/h, peaking at 319 in the 08-19 18:00 hour. Only 1 of 917 was on `/reiseloesung/orte`; the rest are journey search. As a share of upstream calls that is only 2.4 %, but the blast radius is the circuit breaker: 112 opens and 1,239 fast-failed calls in one 3.6 h process window, and **8,852 of 21,119 `/api/journeys` requests answered 503 over the full log — 42 %**. (A shorter 3.6 h window read 23 %; the problem is bigger than the first sample showed.)
- It is load-driven, not random. Bucketing active minutes by inbound rate: ≤10 req/min → 6 % of minutes carry a 429; 11–20 → 20 %; 21–30 → 56 %; 31–50 → 81 %; >50 → 83 %. The knee sits around 20–30 req/min.
- **Heavier caching cannot fix it, and that is a property of the traffic.** Replaying the real access log: 4,376 searches spread over **1,597 distinct route pairs**, ~2.7 searches per route across 3.7 h. Theoretical ceiling with an *infinite* TTL and no eviction — exact key 27.3 %, departure-to-the-hour 33.2 %, departure-to-the-day 41.5 %, ignoring departure entirely 49.7 %. The current config already achieves 20.7 %. Realistic settings: 15-min bucket / 30-min TTL cuts upstream calls 3.7 %, 60-min bucket / 60-min TTL cuts 8.3 %. A 12× TTL increase buys 8 %, and buys it by serving hour-old real-time data on a delay site whose within-TTL hits carry no staleness disclosure (only the stale-fallback path sets `staleSeconds`). `CACHE_MAX` is not a bottleneck either — the simulation is identical at 512 and at 20,000. Left at 300 s / 512.
- **`BAHN_MAX_CONCURRENCY` 4→2 was proposed and then withdrawn.** The semaphore is a concurrency cap, not a rate cap: throughput through it is `concurrency ÷ response time`, so it loosens exactly when bahn.de starts refusing, because a 429 returns almost instantly and recycles the slot. Evidence: counting 429s by the second they landed, single seconds carried 5, 6, 7, 10, 11 and 13 of them — 13 completions through a 4-slot cap means each rejection returned in ~300 ms. At normal volume (~0.5 upstream calls/s) an average call would need to take ~8 s for 4 slots to bind at all, so halving it changes nothing routine while making successful searches queue. What actually holds the line today is the breaker. If a rate lever is ever wanted, the right tool is a token bucket, not a smaller semaphore.
- **Growing `STALE_MAX` was proposed and then withdrawn too.** The first-pass reading of 1,079 stale misses against 33 hits as "the store is too small" is wrong. Replaying all 21,119 searches with their real status codes and populating a simulated stale store from the successes: at `STALE_MAX` 256 the store rescues 1.3 % of the 503s, at 1,024 it rescues 2.1 %, and at **unlimited** it still rescues 2.1 % — the cap stops mattering past ~1,024, so nothing is being evicted. Extending `STALE_TTL` does not save it either: 1 h → 2.1 %, 6 h → 3.6 %, 24 h → 3.9 %, forever → 3.9 %. The store can only hold routes that succeeded *before*, and during an outage the routes being searched mostly never had a prior success — the same long tail. The only way to real coverage is answering a different departure time on a different travel day, measured at a 33.3 % ceiling, which the `STALE_ROUTE_MAX_SKEW` / same-day guards deliberately refuse and should keep refusing.
- **What shipped, because it is the one lever with leverage.** `metrics["searches"]` counts every `bahn_api.journeys()` call including internal ones: 7,107 against 4,376 real `/api/journeys` requests, so **2,731 — 38 % of all journey searches — are the "if you miss this transfer" enrichment**, matching the existing comment at the `MAX_IF_MISSED_REPLANS` gather calling it the biggest multiplier on our upstream rate. Past-mode replans are negligible (93 of 4,376 searches were `mode=past`).
- `_replan` caches raw bahn.de payloads at 100–500 KB each, so `REPLAN_CACHE_MAX` is 500 and `/health` showed it pinned at 500, thrashing. The answer `_if_missed_connection` derives from such a payload measured **0.4–0.8 KB** on live responses. New `_if_missed_cache` in `app/main.py` caches that derived `{legs, arrival}` instead, `BAHN_IF_MISSED_CACHE_MAX` default 10,000 (~a fifth of the memory the 500 raw entries can take; the box has 3.8 GB total, 738 MB RSS, 1.7 GB available). `_replan` and past-mode behaviour are untouched and simply see less churn.
- It caches far better than the search cache can, and for a structural reason: the key is `(origin, dest, ready_minute, window)` where `ready` is a **planned** arrival plus a median delay off the local parquet — timetable-derived, never the searcher's clock — so two people searching the same route hours apart share one entry, where a journey key carries a departure bucket that rolls every 5 minutes. `window` is in the key because it decides the span `leg_delay_stats` summarises. Seen directly in a live response: two journeys both resolving to München-Moosach shared one answer.
- "No catchable connection" **is** cached — a real answer derived from a real payload, and otherwise every such transfer re-asks bahn.de forever. An upstream refusal is **never** cached, since it would suppress the panel on that route until the process restarts; `_replan` returning `None` is now distinguished from "payload had nothing suitable". Staleness across the nightly parquet rebuild is a non-issue: `delaybahn-pipeline.service` ends with `ExecStartPost=systemctl restart delaybahn.service`, so no entry can outlive the `delayStats` it froze.
- **Observability, because the hit rate is argued structurally and not measured.** The app could not log below WARNING at all: uvicorn configures only its own loggers, so `app.*` records fell through to `logging.lastResort`, which hard-drops sub-WARNING — which is why every existing call site is `log.warning`, including non-warnings like the breaker's `closed -> half-open`. `app/main.py` now attaches a `StreamHandler` to the `app` package logger at INFO with a bare `"%(message)s"` formatter, chosen so existing journal lines keep byte-identical shape (`lastResort` emits just the message); verified side by side.
- `_note_upstream(source)` counts at `_issue`'s retry loop — the single point a request goes on the wire, so cache hits, coalesced waiters, circuit-rejected calls and stale fallbacks are all correctly absent, while a 403 profile rotation and a quick 429 retry each count again. `source` threads `_request` → `_issue`; `bahn_api.journeys()` gained `source="search"` by default; `main._replan` takes it and passes `"walk"` or `"if-missed"`; `locations`/`nearby` tag their own. It is deliberately **not** in any cache key, so a walk replan and an if-missed lookup still share an answer. One rollup line per 100 wire calls (`BAHN_UPSTREAM_LOG_EVERY`): `bahn.de upstream: 100 calls in 138s (43.5/min) if-missed=28 locations=12 search=57 walk=3, 429s=3`, where `429s` is the **interval** count, not cumulative. ~18 lines/h at measured volume, against a journal already running ~189k lines/week. A second rollup every 200 if-missed lookups (`BAHN_IF_MISSED_LOG_EVERY`) reports that cache's hit rate. `/health` gains `caches.ifMissed` and per-source `upstream_from_*` totals.
- Verified: **71 pytest** (9 new — the derived answer shared across searches, absence-of-connection cached, upstream refusal never cached, eviction at the cap driven through the real function, the rollup firing once per N lookups with an interval rate rather than a cumulative one, source attribution, cache hits absent from the upstream count, and the upstream rollup's rate and breakdown). `tests/conftest.py` needed the new module state in its per-test reset or counts leak between tests. Log line shapes were rendered and compared against a real `bahn.de 429:` warning. Live measurements were taken by sampling real routes from the access log against the production box.
- Landed alongside another session's nearby-products fix (9bb9c83): its premerge stash pop conflicted on `app/bahn_api.py` and `tests/test_bahn_api.py`, where both changes touch `nearby()`. Resolved so the call site carries both `source="nearby"` and the repeated `products` key; the full suite passing at 71 is what confirms the two coexist.
- Busters: none — backend only, no static asset changed.
- Deliberate non-goals: **if-missed was not made lazy.** Fetching on click was proposed and dropped, because the collapsed button reads `If missed: arrival 18:11` and that time only exists after the replan — hiding it behind a generic "show next connection" is a real downgrade, since the at-a-glance cost of missing the transfer is the feature. `MAX_IF_MISSED_REPLANS` stays at 3: measured over 13 sampled searches, cutting it to 1 removes ~45 % of the buttons for only ~16 % less load (over half of searches have zero tight transfers, so the cap does not bind on most of them). No identity rotation, no widening of the stale-route skew.

- Open and worth watching after deploy: the replan hit rate is a structural argument, not a measurement — the replan keys are in no log. Read the new `bahn.de upstream:` lines: `caches.ifMissed` should climb well past 500 without pinning, `if_missed_hits` should outweigh `if_missed_misses`, and `searches` should close its gap on the `/api/journeys` request count. **If hits come in low the premise was wrong and this should be reverted rather than tuned.** And if `if-missed=` drops sharply while the 503 rate does not follow, the demand side is exhausted and the remaining answer is upstream capacity — official DB API access — not more code.

## 2026-08-21 — One upstream identity at a time: session recycling on budget, age and 403

- bahn.de started returning 403 bursts overnight (ntfy 01:15, then 06:30 + 06:45 CEST — the latter two are one episode plus the watchdog's 10-min reminder, not two). A third burst was in progress while this shipped: 12 `blocked impersonate=` events in the hour to 06:15 UTC at 18–19.8 calls/min. Journal forensics on the two overnight episodes: 69 and 129 events, both intermittent (successes in between) rather than a wholesale block, both self-clearing. The site stayed up on cached/stale data and `/health` stayed 200 throughout, so only the upstream-counter watchdog saw them.
- Root cause: `_sessions` held one `AsyncSession` per impersonation profile for the entire process lifetime, so one long-lived connection and its steadily accumulating cookie jar carried every call — and the only reaction to a 403 was `_rotate()` swapping the TLS fingerprint **in place** on that same session, cycling firefox→safari→chrome within seconds on a client Akamai had already flagged.
- Replaced by **one live identity at a time** — one profile + one cookie jar + one connection, created and discarded as a unit (`_ident`, `_acquire_identity`, `_retire`, `_burn`). Recycled once a per-identity jittered budget of 50–100 requests or 600 s is spent, whichever comes first, so no single session accumulates enough history to be scored as one continuous heavy client. Tunable via `BAHN_SESSION_MIN_REQUESTS` / `BAHN_SESSION_MAX_REQUESTS` / `BAHN_SESSION_MAX_AGE_SECONDS`.
- A 403 now burns the whole identity and advances the profile, so the retry goes out on a fresh session with an empty jar instead of re-presenting the flagged one wearing a different fingerprint. The retry bound (`rotations < len(PROFILES)`), `UpstreamBlocked`, and the breaker's `force_open(30)` are unchanged.
- **A 429 still swaps nothing.** The 2026-08-13 policy stands — count/age recycling is scheduled hygiene, not a reaction to refusals — and is now pinned by a test asserting `session_recycled == 0` on the 429 path.
- Retired sessions are closed by a deferred task 30 s later rather than immediately: curl_cffi's `AsyncSession.close()` is permanent (any later request raises `SessionClosed`) and hard-closes pooled handles, so closing one under an in-flight request would kill that request. 30 s clears the 20 s request timeout. For the same reason the identity is acquired *inside* `_upstream_sem` — a task parked on a semaphore slot must never hold a reference to a session burned under it. `close()` cancels the pending timers and closes current + retiring sessions at shutdown, a path that previously had no test at all.
- New `session_recycled` counter on `/health`; each recycle logs its reason (count / age / 403).
- Tests: **77 pass** (was 72). `conftest`'s `FakeSession` gained `close()` and the `bahn` fixture a factory seam (`holder.factory`) so session construction is observable; 7 new tests cover budget recycle, age recycle, 403-burns-the-session, 429-does-not-swap, the deferred close firing, a fake lacking `close()`, and shutdown draining. ## 2026-08-22 — Install banner on every iOS browser, not just Safari

- Reported from a real iPhone: the install banner never appears in Chrome on iOS. Cause was the platform gate, `isIOSSafari = isIOS && /safari/i.test(ua) && !/crios|fxios|edgios/i.test(ua)` — iOS Chrome/Firefox/Edge failed it and fell through to the Chromium branch, which only shows the banner from inside a `beforeinstallprompt` handler. No iOS browser ever fires that event (they are all WebKit skins with no install API), so those users saw nothing at all: not the banner, not the sheet, not a hint.
- The premise the old gate rested on — "on iOS only Safari can add to the home screen" — has been false since iOS 16.4, which gave third-party browsers the same home-screen web-app mechanism. Chrome for iOS exposes it as Share (right of the address bar) → "Add to Home Screen" → "Add", and because `manifest.json` already declares `display: standalone` the resulting icon launches in its own WebView instead of bouncing to the default browser. The three steps are identical to Safari's; only the lead sentence and where the Share button sits differ.
- `isIOSSafari` replaced by an `iosBrowser` discriminator (`safari`/`chrome`/`firefox`/`edge`, `null` off iOS) and the branch condition relaxed to `isIOS`, so every iOS browser takes the sheet path. When it is not Safari the sheet's lead swaps to `iosSheetLeadChrome` ("In Chrome, in 3 Schritten:") or the generic `iosSheetLeadOther` ("Über das Teilen-Menü deines Browsers…") for Firefox/Edge, assigned through `dataset.i18n` so a DE/EN toggle afterwards keeps it — the same pattern `installLeadDesktop` already uses. The step texts are untouched.
- `track("install", …)` now carries `browser` on the `shown` and `ios-sheet` events, so the Chrome-iOS funnel is separable from Safari's in Umami — worth watching, since this is the first time that segment is addressed at all.
- Busters: `app.js?v=98` → `?v=99` in index.html, `SHELL_VERSION` v32 → v33 and the pinned `/app.js?v=99` in sw.js. `style.css` unchanged, so v73 stays on both sides.
- Verified: `node --check` on app.js and sw.js; the UA branch table exercised against real Safari / Chrome / Firefox / Edge-on-iOS strings (all four → sheet, correct `iosBrowser`) and Android + desktop Chrome (both → `beforeinstallprompt` path, unchanged); `_en_strings()` in app/main.py parses both new keys, 156 entries. Confirmed beforehand that production was still serving the pre-fix `isIOSSafari` at `app.js?v=98`, which is why the user's device test showed no banner.
- Not verified: anything on a physical iPhone — the user tests after this deploy. The open question is whether Chrome-iOS's installed web app reports `display-mode: standalone` or `navigator.standalone`. If it does not, the banner will reappear inside the installed app (that WebView has its own localStorage, so the 60-day dismissal does not carry over either) and the suppression check needs a different signal. Deliberately left alone rather than guessed at.
- Non-goals: no change to the Android/desktop path, no change to the sheet's 3 steps or icons, and no attempt to detect the iOS version — the sheet's instructions are harmless on a pre-16.4 device, where the added shortcut simply opens in the default browser.
