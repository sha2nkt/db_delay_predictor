## Known limitations

- Delay stats are per-train-number history; a rescheduled or renumbered train shows "keine Daten".
- `delays._cache` keys on `(train, eva, window)` while the SQL also filters on time-of-day, so two same-numbered trains calling at one station at different hours can return each other's stats; `_date_cache`/`_dep_date_cache` have the same gap within a day. Deterministic tie-breaking (2026-07-27) fixed result *stability* across rebuilds, not this.
- Load testing runs against recorded fixtures (`pipeline/loadtest_stub.py`); real bahn.de and IRIS behaviour under load is unmeasured by design, and the origin's own capacity is only as good as the upstream latency the stub simulates (250 ms default).
- Walking legs get no badge; since 2026-08-14 they carry their planned duration ("Walk · 7 min · A → B"), which is what the transfer figure was silently subtracting. U-Bahn, tram, city-bus and ferry legs show "nicht erfasst" — IRIS has no data for them (parquet `train_type='Bus'` rows are SEV rail-replacement only, keyed by run number, and municipal stops carry 6-digit non-EVA ids). Sourcing them would need GTFS-RT (DELFI) plus a stop-id crosswalk; deferred.
- On cards with the tight-transfer pill, a non-red median badge is hidden, and with it that card's badge-click day chart.
- The if-missed alternative is a typical-day estimate: readiness at the transfer = planned arrival + the arriving leg's *median* delay, and candidates are filtered on *planned* departures — no live data involved; the alternative's own delay risk shows only via its badges. It excludes FlixTrain since 2026-08-14, same as the past-mode replan.
- Replacement connections are filtered for Flix only. Any other operator outside the DB tariff would still be proposed; bahn.de's "normal (international) tickets not valid" attribute would generalize the rule but was left unused (2026-08-14) because over-excluding inflates claims.
- Journey search covers what bahn.de returns (~6 connections per page; earlier/later buttons fetch adjacent pages).
- bahn.de web API is unofficial and could change without notice; it is bot-protected by Akamai, which blocks one TLS fingerprint at a time (the app rotates through firefox/safari/chrome profiles on a 403, but a simultaneous block of all three pauses the search behind the circuit breaker), and rate-limits per session cookie: sustained traffic 429s the shared jar (2026-08-13 surge outage). Managed — deliberately not evaded — by 5-min departure buckets on the journeys cache, a 300 s TTL, a 4-way upstream concurrency cap, and since 2026-08-13 evening a circuit breaker with `Retry-After` support instead of the short-lived 429 jar-swap/profile rotation (removed as rate-limit evasion). The app degrades instead of failing: journeys answered successfully in the last hour are re-served with a visible age notice, the frontend auto-retries once behind a friendly overload message, upstream throttling surfaces as 503 + `Retry-After` rather than a blanket 502, per-IP limits (our own 429) stop one client from burning the shared budget, and sustained 429s page via ntfy — a route with no answer in the last hour still errors (friendly, not raw). All users still share one upstream session identity at a time by design — since 2026-08-21 that identity is recycled after a jittered 50–100 requests or 600 s and discarded whole on a 403, so no single session accumulates enough history to be scored as one continuous heavy client; if traffic outgrows cache + coalescing, the honest levers are a longer TTL or coarser buckets, not more concurrent identities. Rate-limit windows still occur — bahn.de asks for ~45 s at a time and the shared session sits near its budget edge — but a search now waits one out behind a countdown instead of failing, so users see a slow search rather than an error (a window that outlasts the 75 s retry budget still ends in the friendly message).
- France: Trenitalia France and other non-SNCF operators are absent from the feed; "actual" times are the last realtime projection, not measured; poller downtime creates permanent holes for those hours.
- Switzerland: GESCHAETZT (estimated) actuals are accepted alongside REAL; foreign stops of international trains carry no Swiss actuals (each country's own source covers its own stations).
- Austria: only the ~200 busiest stations are polled (long-tail halts show "keine Daten"); "actual" times are the last HAFAS realtime projection, not measured; poller downtime creates permanent holes for those hours; the board interface is unofficial and could change without notice.
- Italy: runs that never touch one of the 254 discovery hubs are missed; trains changing number mid-run (haCambiNumero) are keyed under the discovered number only; Trenord data in ViaggiaTreno is thin; ~840 minor halts have no bahn.de EVA and are skipped; poller downtime creates permanent holes; the ViaggiaTreno interface is unofficial (no open-data license) and could change without notice.
- Compensation checker: reaches back only as far as the live parquet (~30 days) while DB accepts claims up to 1 year; monthly archives are not wired up yet. The recent end is covered live, so the gap is at the far end only.
- Live same-day lookups are German only (IRIS has no CH/FR stops) and need `DB_API_KEY`/`DB_CLIENT_ID`; without credentials the date picker stops at the parquet's last day, exactly as before. German S-Bahn legs match by line label ("S5") since 2026-08-02 — nearest run of that line within the time-of-day tolerance, which for a headway service is the intended proxy, not an exact-run match.
- Simulation assumes a rational passenger taking the earliest-arriving catchable connection; replacement legs without delay data count as on time; the DB claim page lists only journeys booked in that bahn.de account (form fallback linked).
- The claim modal's bahn.de button labels are best-effort recreations, not captured from the live bahn.de UI; if DB renames its buttons the modal needs a one-line i18n update.
- Feedback screenshots are user-chosen images and may contain personal data (a booking view, a name); the module's "nothing identifying stored" stance now depends on what visitors send. No attach-row hint or impressum wording yet. The 200 MB/day budget bounds the growth rate, not the total — sustained abuse still adds ~6 GB/month until the ntfy warnings are acted on.
- The contact link is a `mailto:` — a visitor without a configured mail client gets nothing when clicking it, and since 2026-08-17 not even a box showing the address first; the anonymous feedback box (or the address printed in the impressum) is the fallback. Feedback comment pushes need `NTFY_TOPIC` in the service environment; without it comments still land in SQLite and the push is skipped — since 2026-08-14 that skip is logged once per process instead of passing unnoticed, which is how it went undetected for four days.
- PWA install prompt shows wherever the browser reports the app installable: Android and desktop Chromium (the omnibox install icon stays available there too — `preventDefault()` only suppresses the mobile mini-infobar) and iOS Safari. Desktop Firefox and desktop Safari never fire `beforeinstallprompt`, so they see no banner. On iOS no browser has an install API, so the prompt there is a bottom sheet with manual Add-to-Home-Screen steps rather than a one-tap install — shown in every iOS browser since 2026-08-22 (before that only Safari got it, and Chrome-on-iOS users saw nothing). Third-party iOS browsers can add a real standalone web app since iOS 16.4, so the steps work in Chrome/Firefox/Edge as well — but only from the share icon in the address bar, never the ⋯ overflow menu, and the row needs scrolling to reach (it can also be hidden entirely if the share sheet's actions were customised, recoverable via "Edit Actions…"); not yet confirmed on a device is whether the resulting Chrome-iOS web app reports `display-mode: standalone`, i.e. whether the banner self-suppresses inside it. The service worker's precache list is pinned to the current `?v=` cache-busters, so a buster bump must also bump `SHELL_VERSION` in sw.js or the shell precache goes stale. (`sw.js` itself is served `no-cache` so the worker isn't edge-cached; deploys before that 2026-08-11 fix could serve a stale worker for up to Cloudflare's ~4 h TTL.)
